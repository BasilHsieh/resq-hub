## 1. 範圍

只有**志工頁**：手機、一次一件事、給最不熟手機的人（[角色輪廓](角色輪廓.md) §1b）。

中繼站（筆電、坐著、一天登記幾十筆）、遠端整理（桌機、看整盤）、兵推主持台（投影）的資訊密度完全不同（[資料模型與狀態機](資料模型與狀態機.md) §5）。那些畫面要做時再加元件，不硬套這一套。

## 2. 兩個版本

| | 第一版（2026-09-27 上午） | 第二版（同日下午，現行） |
|---|---|---|
| 怎麼來的 | 從既有 mockup 原樣抽出來 | Basil：「配色真的好醜」「重新設計，符合 2026」→ 三個方向選 A → 顏色從一個主色推 |
| 長相 | 米色底、深藍、每樣東西都框一個細框 | 清楚大膽：大數字分類格、色塊代替框線、膠囊按鈕、24–28px 圓角、答案放畫面下方 |
| 顏色 | 深藍＋米色＋橘＋灰（沒有推導） | 主色「靛」＋只給缺人的「杏橘」＋帶一點主色的灰；全部由 `scripts/ds.py palette` 算出 |
| 字 | 蘋方優先，字重 400–700 | 數字與英文用 SF／Roboto、中文蘋方／思源黑體；標題與數字 800 |
| 演習標記 | 紫色斜紋條 | 深色細條（產品裡沒有別的深色條） |

## 3. 第二版的決定與理由

| 決定 | 理由 | 否決的選項 |
|---|---|---|
| **長相用 A「清楚大膽」**（Basil 選） | 大數字、色塊、膠囊按鈕是 2026 年的共同語言；Google 為 Material 3 Expressive 做的研究（46 場、18,000 多人）發現這類設計讓人更快找到關鍵按鈕，45 歲以上跟年輕人一樣快——正是我們的使用者 | B 戶外高對比（黑白加安全黃：太陽下最清楚，但像警報、比較硬）；C 安心原生（像 iPhone 內建 app：最安心，但一眼掃過去最不醒目） |
| **不在 Apple 與 Google 之間選邊**（Basil 更正） | 真的做成 app 時，導覽列、系統按鈕本來就會跟著平台（iPhone 的液態玻璃、Android 的 Material 3），避不掉也不用避；現在要定的只是內容的風格：顏色、字、形狀、元件 | Claude 原本把「2026」講成液態玻璃 vs Material 3 二選一——把平台元件跟品牌風格混在一起了 |
| **內容區不透明、不用陰影** | 液態玻璃推出後一直被批評不好讀，大太陽下尤其明顯（Apple 在 iOS 26.1 加了降低透明的選項）；陰影在太陽下也看不到。平台的導覽列可以是玻璃，我們的內容不要 | 半透明卡片、霧化底 |
| **顏色從一個主色推出來**（Basil 提方法，Claude 做推導） | 一個主色、一個暖色（只給缺人），其他全部是帶一點主色的灰。色相少，畫面就不吵；每個顏色有來處，換主色整套一起換 | A 第一次的配色：Tailwind 預設藍＋綠＋橘＋紫四個色相互搶，看起來像範本 |
| **主色：靛** `oklch(0.48 0.15 276)`（Claude 提，Basil 確認） | 三個候選裡最現代、最親切；杏橘是它的對面，缺人一眼跳出來；靛偏紫，跟國民黨的正藍有距離。Basil：現場沒有特別會撞到的顏色（單一觀察者） | **深青**：最安靜，但接近民眾黨的青綠；**墨**：最素、缺人最跳，但整片黑在有人罹難的災區可能太沉（黑白是喪事的顏色）。三個都在 mockup 的「主色」頁 |
| **暖色只給缺人** | 清單上第一眼跳出來的，就是需要人的戶（D-15 要解決的「沒有人知道」） | 同意也給一個顏色（綠）——多一個色相，而且「已同意」用主色的淺色就夠 |
| **中性色帶一點主色**，頁面底色比卡片暗一點 | 白卡片放在同樣白的底上，太陽下分不出邊；A 原本就是這個做法 | 暖米色中性（試過：又回到第一版被嫌醜的米色） |
| **字重拉開層次**：標題與數字 800、標籤 700、內文 400；數字與英文用系統的 SF／Roboto | 大數字要夠粗才像 2026；蘋方最粗只到 600，所以數字交給 SF | 載入網路字型換更粗的中文（災區網路，照樣不做） |
| **答案按鈕靠左、圖示放在白圓裡、放在畫面下方** | 大拇指按得到；圖示＋粗字＋副標，三層一眼分清 | 置中的大按鈕（第一版） |
| **強調框 2.5px 畫在卡片裡面** | 展開、你剛剛在、要你先按的那一塊要夠明顯；畫在裡面不會讓版面跳動 | 1–2px 細框（太陽下不夠） |
| **演習標記改成深色細條** | 紫色斜紋太搶；產品畫面裡沒有別的深色條，一樣不會跟狀態混淆 | — |
| **對比由 `kb.py check` 擋** | 每組文字 6.5:1、邊框 3:1 寫成檢查，誰改了顏色都會被擋下，不用靠記得 | 只寫在文件裡 |
| **mockup 每一張都用設計系統的元件組成**（2026-09-28 起由志工頁互動版接手，D-18） | 設計系統改了（例如換主色），畫面跟著換，不會一邊一個樣子 | 在畫布上手刻長得像的標記（第一版的做法，會漂移） |

## 4. 第一版留下來的決定

| 決定 | 理由 | 否決的選項 |
|---|---|---|
| **只有淺色主題** | 白天戶外用，陽光下淺底深字最好讀 | 跟著手機切深色模式（晚上刺眼的問題，等有人反映再做） |
| **不載入網路字型** | 災區網路不穩，中文字型檔很大，載不到就空白或閃一下 | 從 Google Fonts 載 Noto Sans TC |
| **可按範圍至少 48px** | 規格假設戴手套（§5）；一般手機的 44px 不夠 | 44px |
| **每組文字對比 6.5:1 以上** | 太陽下看；WCAG 的 4.5:1 是室內標準 | — |
| **產品裡的字最小 15px**；演習標記 13px 是唯一例外 | 以最不熟手機的人為準；演習標記上線時整條拿掉 | 14px 的註腳 |
| **形狀帶意思：虛線＝還沒確定** | 「尚未取得同意」「還沒問到」都是還不知道；實線框＝確定的「不」；填色＝確定的「是」或缺人 | 只用顏色區分（色弱、陽光下都分不出來） |
| **元件上的中文字寫死** | 分類名、按鈕字、時間寫法是 D-16 的決定；開放傳字進來，程式就會偷偷跟規格不一樣（D-13） | 字由使用元件的人傳入 |
| **需求標籤只講人力** | U-06 的候選原則：物資廣播供給、需求一對一。清單上掛「便當 20 個」，五路人馬會各送一份 | mockup 原本的「缺 2 人、便當 20 個（17:00 前）」——已拿掉 |
| **元件用 React 寫，可以按的都收 `href` 或 `onClick`** | 同一套元件給 mockup 串頁和之後真的 app 用 | 只給規格文件、不給程式 |
| **bundle.css 帶一份 specificity 0 的預設值** | repo 裡的 prototype 不用另外產生 tokens.css 就能用；有 tokens.css 時一律由它決定 | 每個 prototype 自己抄一份色碼 |

## 5. 怎麼維護

- **以 repo 為準**：`output/design-system/tokens.json` 是唯一真相；顏色由其中 `meta.palette` 的主色推出來。
- **換主色**：`python3 scripts/ds.py palette <主色hue> <主色chroma> <中性hue> <缺人hue>`（現在是 `276 0.15 270 60`；深青 `192 0.085 200 48`；墨 `60 0.014 60 45`），會重算顏色、檢查對比、更新 bundle.css 的預設值。
- **不會漂移**：`kb.py index` 會重新生成 bundle.css 的預設值；`kb.py check` 會檢查 token、對比、預設值是否過期、顏色是不是被手改過、每個元件有沒有說明與預覽。CI 也跑同一份。
- **長相有基準圖**（D-19）：志工頁「所有狀態一次攤開」每一格一張，放在 `output/prototype/03-志工頁/screens/linux/`，每個 PR 自動截圖比對。改了元件或 token、畫面跟著變，基準圖要在同一個 PR 一起更新，Basil 在 PR 裡看前後對照。顏色的細微變化（色碼差 2～4）截圖抓不到，由上一條的 token 檢查負責。做法見 [03-志工頁 README](../prototype/03-志工頁/README.md) 第 5 節。
- **發布**：改了 repo 就重新發布 artifact（`python3 scripts/ds.py stage <資料夾>` 會照 artifact 的路徑排好）；志工頁互動版發布時一起帶上最新的 `components/bundle.css` 與 `bundle.js`（做法見 03 README 第 5 節）。
- **只透過 AI 改**（Basil 2026-09-27，D-17）：人不在設計系統頁或畫布上直接調整，流向是單向的 repo → 網頁，不需要同步回來。萬一網頁上被人改過，發布時工具會因為版本對不上而拒絕，那時先讀回來看改了什麼。
- **志工頁也以 repo 為準**：`output/prototype/03-志工頁/app/` 用設計系統的元件做成可以點的程式，「所有狀態一次攤開」也從它產生（做法見 [03-志工頁 README](../prototype/03-志工頁/README.md) 第 5 節）。原本產生畫布 mockup 的程式已封存（D-18）。
- **對應關係**：artifact 的 `project/<路徑>` ＝ `output/design-system/<路徑>`；artifact 自己的索引 `project/design-system.json` 與它生成的 `tokens.css`、`api/`、`manifest.json` 不進 repo。

## 6. 不做

半透明與霧化、陰影層次、動畫、網路字型、深色模式（這一版）、只靠顏色的狀態、只有圖示的按鈕（返回鍵除外）、排行／分數／打卡。

## 7. 還沒定的

- 🚧 **網路不穩時「還沒送出」的樣子**。離線是真產品架構，D-12 已決定現在不做，所以設計系統先不畫。在那之前，「下一個打開的人會看到」這種話只有真的送出後才能寫。
- 🚧 **陽光下實測**：淺色塊（`tonal`）和輔助文字（`ink-3`）在戶外夠不夠。兵推可以順便帶一支手機到戶外看一次。
- 🚧 **清單預設停在哪一類**（D-16，交給兵推測）。
- 中繼站、遠端整理、主持台的元件：要做那些畫面時再加。

## 8. 交給實作的人：怎麼讓成品跟設計大致一樣

2026-09-27 與 Basil 的討論。起點是他另一個專案（原生 app）的經驗：HTML 線框做出來的 app 跟線框差很多。那一頁的差異分成四類，這裡記下哪些擋得住、怎麼擋。

- **走樣的主因是「重做」**：設計和成品各有一份，實作的人（或 AI）看著設計、用另一種技術重寫。每重寫一樣東西，就多一次做不同選擇的機會：工具的預設值會贏（欄位變成上下疊的大輸入框、底部面板變成畫面中間的泡泡）、看不到用意所以「好心改掉」（刪除鈕貼到完成鈕下面）、小差異累積成「感覺不一樣」。
- **要 100%，只有一個方法：不要轉換。** 設計稿直接用產品的元件做，實作只剩接資料和行為——就是本設計系統與志工頁的做法（畫面都是設計系統元件：演習時放假資料，產品放真資料）。Figma 最接近 100% 的做法（把設計元件連到真的程式元件）也是這個原理；任何「把設計稿轉成程式」的工具都得猜設計稿沒寫的資訊，所以到不了 100%，跟工具強不強無關。
- **志工頁是網頁**（一個網址、不裝 app，角色輪廓 §1b），所以接手的人可以直接用 `output/design-system/components/` 的元件，這一步沒有翻譯。**前提是他真的用**：交接時的第一條規則是「畫面只准用設計系統的元件拼，不重畫」。D-18 之後更直接：接手的人接著做同一份程式。D-19（2026-10-01）：演習版全部畫面都是網頁；災時真正要用的那一套要不要做原生 app，等驗證做得起來再跟工程師討論。
- **如果之後改做原生 app**（D-19：災時那一套要不要原生還沒定，這一段就是到時候的做法），翻譯避不掉，改成「共用定義、每個元件只翻譯一次」：① 顏色、字級、用字從同一份檔自動轉成 iOS、Android 的程式（例如 Style Dictionary），不手抄；② 每個設計系統元件在原生端各做一個同名、同狀態、同用字的元件，畫面只准用它們拼，不拿系統預設元件代替；③ 每個元件的用意寫在旁邊，不准自己改；④ 每個元件、每種狀態自動截圖比對，差太多就不算完成；⑤ 或選跨平台框架（React Native 跟現在的 React 元件最接近）。
- **擋不住的**：設計稿沒畫到的情況、只寫在文字規格裡的規則（例如「刪除要先問」），不管網頁還是原生都會被實作的人自己發明。只能靠先決定，或明確標 U-XX／🚧「還沒定、要先問」；只寫在文字裡的跨畫面規則，最好也做成元件。
- **做完一定要對照**：成品截圖跟設計逐條比（Basil 另一個專案的「app vs 線框」對照頁就是這個做法），差異修完才算完成。這一步現在的做法取代不了。**2026-10-01 起自動化了一半（D-19）**：志工頁每一格的截圖，每個 PR 自動跟基準圖比。它比的是「跟上一次點頭的樣子一不一樣」，不是「對不對」——第一次對不對、沒畫到的情況，還是要人看。
- **不是 Claude 的協作者**：Codex 讀的是 `AGENTS.md`，不是 `CLAUDE.md`。有人用 Codex 加入時，要把 `CLAUDE.md` 的規則也給它一份，例如「程式不准偷偷跟 spec 不一樣」「畫面一律用設計系統」。
- 🚧 **以上是推論，還沒驗證**。最便宜的驗證：找一張畫面，請另一個 AI（例如 Codex）只看 repo 做出來，再跟畫布比。有了截圖比對之後更便宜：請它接著改同一份程式，看 16 張基準圖有沒有變。
