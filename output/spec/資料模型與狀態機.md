## 0. 一個決定：名單先存在，狀態後填

需要幫忙的單位絕大部分是**家戶**（有地址的地方）。地址名單在災害發生前就存在，不需要等任何人回報。

這個決定的後果比它看起來大。地圖不再是「有人回報過的點」，而是**一份完整的名單，每一戶都要交代一個狀態**。因此：

- ⚪（沒人去過）從「空白」變成**可以數的清單**。
- 覆蓋率、冷區停留時間變成可計算的數字（U-09 的 North Star 候選因此有了定義）。
- U-03（冷區怎麼偵測）從「需要演算法偵測」變成「名單減掉已覆蓋」。

## 0b. 修訂（2026-09-22）：回報是現場當下的請求，精準可得

過程留著，因為轉折比結論值錢：

1. Basil：一般志工收工時只講得出「大概方向」＋「缺不缺人」，講不出門牌、內容、數量。Claude 據此把志工回報的粒度降到街段。
2. Basil 再修正：**回報應該要精準，而且合理的情境是人在現場當下**——「現在缺 5 人」「中午要 50 個便當」。收工時的模糊是錯的時刻造成的，不是志工的極限。

因此：

- **回報的時刻＝需求出現的當下，在現場。** 位置由手機在送出時一次性附上（不是追蹤），數量由現場判斷。粒度回到家戶／地點。
- **回報是請求，不是觀察。** 講的人自己是受益者（希望人來、便當到）——這是 U-01 誘因問題第一個站得住的答案：回報的人就是需要它被回報的人。
- **需求有種類與時限**：種類（人力／物資如便當、水／機具／醫療）、數量、需要的時間（「中午前」）。過了時限自動作廢。「50 個便當」即災區內的物資需求，與人力需求同一套（呼應 U-06 的切法：呈現在哪缺什麼，不管庫存與發放）。
- **新的不對稱**：請求源源不絕（自利），「這裡好了」沒人有動機講（利他）→ 地圖會高估需求。對策：因 🔴 而來、發現人太多的志工按「🟠 滿了」（Basil：來來去去的人也會回報，「我去了發現人滿了，就回報這邊滿了」）——他的動機也是自利：按下去的下一秒畫面直接回答「那你去哪」。**白跑的成本變成阻止下一個白跑的訊號，這是 U-12 的主要解藥。**
- **中繼站降為備案**，收工快照降為補充。街段粒度只適用於事後補報。
- 不變：三態、⚪ 為一級狀態、褪色規則、名單當分母。

**誰提出請求（Basil 2026-09-22 的現場觀察，全文見 [馬太鞍溪觀察_basil_2026](../../knowledge/fieldwork/馬太鞍溪觀察_basil_2026.md) 第八節）**：每個需要人力的地方都會湧現一個「領袖」——沒有職務、沒有推舉，願意跳出來的人。他看到需求就上街找人、大批志工經過就喊「這邊大概需要幾個人」。
- **設計結論**：任何人都可以提出請求（D-01），系統不辨識也不驗證「領袖」；實際上提出的多半是那個湧現的人。
- **數字不驗證**：沒有判準、不精準，靠現場的市場機制滾動修正（太多就有人退場、不夠就再喊）。這部分回答 U-05：需求的質不量化，用**種類＋粗略數量＋時限**，各種類精度不同（便當可數、水以箱估、機具只記種類）。
- **站點可以是湧現的**：大型家戶甚至有自己的醫療站。站點物件不限官方。
- ⚠️ **工具會製造的新問題（U-12）**：現場的市場修正發生在走路距離、幾分鐘內；地圖把喊聲送到幾千個還沒出發的人，修正延遲變成車程。設計要求：需求旁必須看得到「多久前喊的」與擁擠訊號（例如「已有 N 人表示要去」——這是能見度，不是配對）；人力需求的褪色以小時計。

## 0c. 名單從哪來（2026-09-26，D-15）

名單是工具的核心：沒人去的地方不會有回報，能讓「沒有人知道」被看見的只有名單。

- **圈出災區**，用公開資料列出圈內住戶（門牌點位、通用電子地圖的建物圖層）。平時就備好全台資料，還是災時當下建——技術問題，未定 🚧。
- **違建普遍，公開資料沒有**：熟悉當地的人可以新增、修改，都留紀錄（只記角色與管道，不記人）。「有建物、沒門牌」的地方由系統先列為候選，請在地人確認。兩份資料能否比對，待查 🚧。
- **不能刪**。刪一戶等於把它從分母拿掉，完成率就變好看——官方 9/30 剔除「不堪使用」的房子就是這樣（見 [光復家戶清淤官方進度_2025](../../knowledge/context/光復家戶清淤官方進度_2025.md)）。「聯絡不上屋主」是「尚未取得同意」（§0d）；「沒人住、已拆」用 ⛔，而且只能經由問里長確認。兩者都留在名單與分母裡。見例 10。
- **里長不必自己操作系統**：Basil 判斷里長與在地人災時期望值低（忙、也可能沒有能力），可行的是**有人去問他們**，由問的人輸入（管道記「問里長／在地人」）。名單也可以平時補。部落要能自己決定要不要被放上名單（U-04、U-13）。

## 0d. 家戶要先取得同意（2026-09-26，D-16）

進到人家家裡要先取得同意（Basil）。所以家戶有兩個**各自獨立**的狀態：同意狀態，和需求（工作狀態）。~~同意之後才有工作狀態~~——2026-09-27 修訂（Basil）：屋主還沒答應，那一戶照樣可能滿屋子泥、鄰居也可能已經知道缺幾個人；很多人也只知道其中一項。兩項各自回報、各自顯示最新一筆和時間；**要不要進門只看同意**。

| 同意狀態 | 在哪個分類 | 需求 |
|---|---|---|
| 尚未取得同意 | 「要先問屋主」，附「最後更新 HH:MM」；完全沒有紀錄寫「還沒有紀錄」。**不寫原因** | 可以已知（例如鄰居說缺 5 人），同一列一起顯示；不知道就不寫 |
| 不同意 | 「不同意」，附「最後更新 HH:MM」，看得到也能更新；**不設過期** | 不顯示 |
| 已同意 | 缺人或需求不明 →「可以直接幫忙」；人夠了、清完了 →「暫時不用去」 | §2 的狀態機 |

- **回報的畫面**（2026-09-27）：清單上點一戶 →「回報這一戶」（原本叫「我到了」——那是時機不是動作，也像打卡報位置）→ 這一戶的頁面上，同意狀態和需求分成兩塊、各有「更新」，只填你知道的那一項。公共區域只有需求那一塊。做完要離開時，從清單上方「你剛剛在」回到這一戶更新需求。

- **清單上要看得出能不能進去**（Basil 2026-09-26）：每一戶分開顯示同意狀態（已同意／尚未取得同意；地點標「公共區域」）和需求（缺幾人），不混成一個標籤。清單上方直接說明「已同意：可以直接進去幫忙；尚未取得同意：先敲門問屋主」。
- **到了發現裡面已經有志工在做，就是已同意**（Basil）：不用再問屋主。清單上已經是「已同意」的戶，到了直接問需求。
- **時間一律寫「最後更新 HH:MM」**（前一天寫「昨天 HH:MM」），不用「N 小時前喊的」「剛有人問過」這類口語（Basil：沒人看得懂）。
- **沒人在家不是一種狀態**，它等於「尚未取得同意」（Basil）。任何畫面都不說有沒有人在——隱私與防盜的問題因此消失。
- **屋主自己喊「缺 N 人」就是同意**，不用另外問。
- **以最新的一筆為準**：屋主可以改變主意。
- **同意是一個會變的狀態，不設過期**（Basil 2026-09-27）：三種值都可能隨時間改變（屋主回來了、要去別處工作了），畫面一律顯示最新的一筆和最後更新時間，看的人自己判斷。**藏起來的狀態就不會被更新**，所以「不同意」不隱藏，改放在清單的另一段。
- **四個分類放在頁面最上面（兩排兩列的大按鈕），直接寫數量，照「現在該做什麼」分**（2026-09-27）：
  - 可以直接幫忙＝已同意的戶（缺人、需求不明）＋公共區域——預設停在這裡
  - 要先問屋主＝尚未取得同意
  - 不同意
  - 暫時不用去＝人夠了、清完了（Basil 2026-09-27 同意改名）。對要挑下一戶的人，兩者的答案一樣；意思不同之處寫在每一戶自己的標籤上。「暫時」是真的：人夠了超過 3 小時、清完了超過 24 小時沒人更新，就回到「可以直接幫忙」、標「需求不明」（§2 褪色規則；兩個時間驗證時再調）
  每個分類內照走路距離排。過程：Basil 提頂端分類＋數量；Claude 一度改成同一頁往下分段（Basil 指出清單一長下面就滑不到，真實規模是上千戶）；接著 Claude 把「尚未取得同意」放進「可以去」（Basil 指出「可以去」跟「尚未取得同意」是兩件事——又一次把兩層綁在一起）。
  🚧 預設停在哪一個分類，是 D-15 的取捨：「要先問屋主」正是要讓人看見的戶，放第二個可能較少人點。兵推可以直接測哪個預設讓更多戶被問到。
- **清單上的「最後更新」＝這一戶最近一筆回報的時間**，同意或需求都算（Claude 決定，2026-09-28，互動版照做）；回報頁的兩塊各寫各的時間。
- 🚧 **進不去（⏸）的戶放哪一類、怎麼顯示**還沒定；互動版暫時放「暫時不用去」、不顯示需求標籤，志工頁也沒有回報 ⏸ 的按鈕。
- **清單只列附近**（Claude 決定）：你附近走路 15 分鐘內的戶，數量也只算附近的。15 分鐘是先訂的數字，驗證時再調 🚧。
- **「已同意」涵蓋現場的三種情況**（Basil 2026-09-27 顧問回答）：屋主或家人說好、裡面已經有人在做、帶隊的人叫你進去。
- **按「不同意」後**，畫面提醒志工跟屋主說一句「之後需要幫忙，跟任何志工說就可以」——改變主意最可靠的來源是屋主自己。
- **工具上的「同意」是給下一個人看的資訊，不是進門的許可**：到了門口仍要先跟屋主打招呼。
- **聯絡不上屋主的戶**會一直停在「尚未取得同意」（光復那 89 戶「受損嚴重或無法聯繫」就是）。問過 N 次仍未取得的，列給「去問里長怎麼找到屋主」的人（D-15）；對外仍只顯示「尚未取得同意」。N 未定 🚧。空屋只能經由這條路確認，志工不能自己標空屋。
- **路段、側溝等地點不需要同意**，直接套 §2。

## 1. 物件

### 家戶

| 欄位 | 說明 |
|---|---|
| id | |
| 地址 | 路街 + 號；樓、戶為選填（見 §6，不做 3D） |
| 座標 | 示意圖上的位置 |
| 村里 | 聚合統計用 |
| 用途 | 住宅 / 非住宅 |

**沒有**姓名、電話、住戶人數、弱勢標記。理由見 §4。

### 地點（非家戶）

路段、側溝、公共空間、農地。清淤與退潮期有大量工作不是家戶形狀的，沒有這類物件會無法表達。

欄位：id、名稱、範圍、村里。狀態機與家戶共用。

### 回報

| 欄位 | 說明 |
|---|---|
| id、時間 | 時間＝**該狀態被觀察到的時間**（志工離開現場的時間），不是送出或登記的時間。代為登記時由登記員問「大概幾點離開」 |
| 對象 | 一個家戶或一個地點；位置由送出時的一次性定位對應（§0b） |
| 狀態 | 見 §2 |
| 同意 | 只用於家戶：尚未取得（有人問過）／不同意／同意，見 §0d。屋主自己喊的請求自動帶「同意」 |
| 需求 | 種類（人力／物資／機具／醫療）＋ 數量 ＋ 需要的時間（時限）🚧 U-05 的「質」如何表達仍未解 |
| 來源角色 | 誰看到的：志工 / 居民（回報是動作不是角色；記角色不記人） |
| 管道 | 怎麼進來的：自己送出 / 顧站代為登記 / 里長代報 / 遠端整理 |
| 備註 | 一句話 |
| 可再看時間 | 只有「進不去」用得到 |

**沒有使用者欄位。**「收情報之前不問你是誰」這個決定寫在資料模型裡，不是寫在文件裡（D-01）。來源只記角色，不記人。

### 站點

醫療站 / 物資站：id、類型、位置、目前狀況。

## 2. 狀態機

狀態**不儲存**，由回報記錄推導：`狀態(對象, 現在) = f(這個對象的回報歷程, 現在)`。

這樣褪色會自動發生，不需要另外維護；而且留下完整歷程，D-07 說的「誰在哪、誰重複去了、哪裡漏了」就在這份歷程裡。

| 狀態 | 定義 |
|---|---|
| ⚪ 未知 | 從來沒有任何回報 |
| 🔴 有需求 | 最近一筆回報說有需求 |
| 🟠 人夠了（滿） | 最近一筆說「這邊滿了」：有需求但已有足夠的人，別再來。**不是清完**（Basil 2026-09-22） |
| 🟢 已覆蓋 | 最近一筆回報說有人看過、暫時沒事／清完了 |
| ⛔ 不需處理 | 空屋，或屋主自行處理完畢 |
| ⏸ 進不去 | 屋主同意、有需求，但現在做不了（等機具、等水退），附可再看時間。屋主不在或還沒答應**不是** ⏸，是「尚未取得同意」（§0d） |

家戶的需求（🔴🟠🟢⏸）和同意狀態各自獨立（§0d，2026-09-27 修訂；原為「只在同意之後出現」）；家戶的 ⚪ 就是「尚未取得同意・還沒有紀錄」。地點沒有同意這一層。

### 褪色是不對稱的

| | 過期之後 | 為什麼 |
|---|---|---|
| 🟠 | → ⚪（門檻以小時計，比 🟢 短） | 那批人走了可能又缺人；過期就回到不知道，讓領袖重喊 |
| 🟢 | → ⚪ | 「沒事」會過期。上游再沖泥就翻回 🔴，不能繼續主張沒事 |
| 🔴 | 仍然是 🔴，但標「情報已舊 N 小時」 | **需求不會自己消失。** 把它降級成 ⚪ 等於謊報 |
| ⛔ | 不褪色 | 結構性的狀態，除非有新回報推翻 |
| ⏸ | 過了可再看時間 → 待重新確認（視同 ⚪，但保留歷程） | |

⚪ 也要顯示「從災害開始到現在，多久沒有人去過」。

**顯示（2026-09-26，Basil，見 §0d）**：時間一律寫「最後更新 HH:MM」。下面例子裡的「情報已舊 N 小時」「N 小時前」是舊寫法，只改顯示、判斷規則不變。

## 3. 界線：名單用來揭露，不用來指派

家戶名單天生長得像工單系統，而**工單也是一種媒合**（命題 1，見 [馬太鞍溪觀察_basil_2026](../../knowledge/fieldwork/馬太鞍溪觀察_basil_2026.md)）。Crisis Cleanup 與慈濟的圖資平台都是派工導向。

所以寫死：

- ✅ 名單用來算覆蓋率、讓沒人去過的戶現形、廣播需求狀態
- ❌ 不把某一戶指派給某個人或某支隊伍
- ❌ 不做認領、不做額滿關閉、不做工單狀態流轉（光復超人 v2.0 的 Uber Eats 派單邏輯正是這個，見 [馬太鞍溪實際使用工具盤點_2025](../../knowledge/context/馬太鞍溪實際使用工具盤點_2025.md)）

依據 D-03。

## 4. 界線：名單是公開的，狀態不是

「地址是公開資料」成立，但**寫在地址上的狀態，是關於可識別住戶的資訊**。而且單位從區域換成家戶之後，隱私的承受者就從志工換成災民——志工可以自己決定要不要被看見，災民不能。

- 不記任何住戶屬性（姓名、人數、年齡、弱勢標記）
- **請求必須帶地址並公開**（2026-09-23，Basil）：需求是當事人自己喊「我這裡要人／要物資」，地址是它的目的，不帶地址沒人能滿足它。~~聚合只適用於**他人觀察到的狀態**（這戶沒人在、不需處理）——那才是別人替住戶貼標籤。因此對外畫面：需求清單逐筆帶地址；觀察性狀態聚合到街或村里~~
- **2026-09-26 修訂（Basil，D-16）**：家戶**一戶一戶列出**——要找得到「巷子的巷子」就要門牌。敏感的狀態不再靠聚合保護，而是根本不顯示：沒人在家併入「尚未取得同意」，空屋與不同意不列出、只算數量（§0d）。
- 「哪幾戶沒人在」本身就是敏感資訊——所以任何畫面都不說
- 🚧 哪些欄位對誰開放，未解，見 U-04

## 5. 角色與裝置（⚠️ 待 Basil 確認）

**裝置不是美術問題，是論證的一部分。**「半分鐘內完成回報」這個主張，只有在手機尺寸、單手、戴手套的條件下展示才算證明過；放在桌機大畫面上展示等於沒證明。

| 角色 | 裝置 | 介面必須遵守 |
|---|---|---|
| 去幫忙的人（同時是情報提供者） | 手機 | 一次只問一件事；大按鈕；幾乎不打字，用選項與預設值；假設太陽下、戴手套、網路不穩 |
| 中繼站的人（報到站、還鏟子點、物資站後面的人；Basil 命名） | 筆電或平板，坐著 | 一天要登記幾十筆，速度優先：清單式、可連續輸入、不要一次一頁 |
| 遠端整理資訊的人 | 桌機 | 資訊密度高：地圖與清單並排，可同時看多筆 |
| 兵推主持人（只有兵推模式有） | 投影大螢幕 | 字大、一眼看懂；參數與事件注入在同一頁 |

同一份資料，三種裝置，三種資訊密度：**手機一次一題，桌機看整盤。**

兵推第一局是單機（接大螢幕），所以每個角色的畫面會**畫在對應的裝置外框裡**（手機框、筆電框），由主持人切換角色。之後若要把連結發給個人自己試，志工那一頁必須在真手機上真的能用。

## 6. 明確不做

- **樓層與 3D**。光復是平地洪災；欄位留著，但畫面是平面的。（光復超人的技術規劃也是大樓火災用 3D、平地洪災用平面模組）
- 登入、身分驗證
- 個人位置追蹤
- 物資庫存與發放、收容中心系統
- 任何審核或驗證機制（可信度靠更新頻率，D-03）

## 7. 驗收條件（spec by example）

每個例子同時是三件事：**Basil 校對的對象、程式裡的測試案例、工程師未來的驗收條件**。時間都是想定裡的模擬時鐘。D-18 起，這些例子要寫成會自動跑的測試、跟志工頁的程式放在一起：測試沒過，程式就不能改——這就是「動態規格」，程式本身不算。

**例 1 · 從來沒人去過的戶**
大全街 12 號從災害發生到現在沒有任何回報
→ 顯示 ⚪，並標「已經 5 天沒人去過」
→ 覆蓋率的分母包含它，分子不包含

**例 2 · 需求不會自己消失**
T+4天 14:00 有人回報「大全街 12 號，缺 3 人」
到 T+5天 08:00 沒有任何新回報
→ 仍然是 🔴，標「情報已舊 18 小時」
→ **不得**變成 ⚪（那等於謊報「沒人知道這裡有事」）

**例 3 · 「沒事」會過期**
T+4天 14:00 回報「大同街 3 號，有人看過，暫時沒事」（🟢 有效 24 小時）
現在是 T+5天 15:00
→ 變成 ⚪，標「上次確認是 25 小時前」
→ 不得繼續顯示 🟢

**例 4 · 兩筆衝突取最新**
T+5天 09:00 有人回報「缺 2 人」
T+5天 11:00 另一個人回報「已經清完了」
→ 顯示 🟢（採 11:00 那筆）
→ 09:00 那筆留在歷程裡，不刪除

**例 5 · 進不去的戶**（2026-09-26 改寫：原例是「屋主不在」，依 §0d 那是「尚未取得同意」，不是 ⏸。規則本身不變）
T+5天 10:00 回報「屋主同意，但要等怪手，預計 T+7天 可再看」
T+6天 全天 → 顯示 ⏸，且**不計入**缺工人數
T+7天 00:00 之後 → 變成待重新確認（視同 ⚪，但看得到 T+5天 那筆歷程）

**例 6 · 時間往前走不會讓情況變好**
任何對象在沒有新回報的情況下快轉任意時間
→ 狀態只能維持，或往 ⚪／情報已舊的方向走
→ **絕不可能**從 ⚪ 自己變成 🟢 或 🔴

**例 7 · 空屋不褪色**
T+4天 回報「大全街 20 號是空屋，不需處理」
T+9天（五天後）→ 仍然是 ⛔，不褪回 ⚪
→ 除非有新回報推翻

**例 8 · 滿了不是清完了**
T+5天 09:00 領袖回報「大全街 12 號，缺 5 人」
T+5天 10:00 一個志工到了，回報「這邊滿了」
→ 顯示 🟠 人夠了；「該去哪」不再建議這裡
→ 覆蓋率（曾有人到過）的分子**會**增加，但「完成」不增加——🟠 是到過但沒做完

**例 9 · 滿了會過期**
承例 8，🟠 門檻 3 小時，現在是 T+5天 13:30，沒有新回報
→ 變成 ⚪，標「上次消息是 3.5 小時前：當時人夠了」
→ 不得繼續顯示 🟠，也不得自動回到 🔴

**例 10 · 名單不能刪，只能標記**（01 單機版沒有名單編輯，未實作）
T+6天 有人到大全街 30 號，房子已不堪使用、聯絡不上屋主
→ 大全街 30 號仍在名單裡，顯示「尚未取得同意」與這次的更新時間，不寫原因
→ 覆蓋率的分母**不變**
T+7天 有人去問里長，里長說「大全街 32 號沒人住」
→ ⛔ 不需處理，不列在「選下一戶」，仍在名單與分母裡；歷程看得到是 T+7天、經由問里長
→ 系統**沒有**任何動作能讓一戶從名單消失

**例 11 · 沒人在家不會被說出來**（D-16，01 未實作）
T+6天 09:00 志工到中山路 45 巷 6 弄 3 號，沒人回應，按「還沒取得同意」
→ 名單顯示「尚未取得同意」與「最後更新 09:00」
→ 任何畫面都**不得**出現「沒人在家」「空屋」

**例 12 · 不同意就不再推人過去**（D-16，01 未實作）
T+6天 10:00 屋主說不用
→ 移到清單的「不同意」那一段，顯示「不同意・最後更新 10:00」，不出現在「可以去」
→ 快轉任意時間都不會自己變回「尚未取得同意」或「已同意」；只有新的一筆能改變它（2026-09-27 修訂：原為「不列在清單上」，但藏起來就沒人能更新）

**例 13 · 屋主自己喊就是同意**（D-16，01 未實作）
T+6天 08:00 屋主自己回報「大全街 20 號缺 5 人」
→ 顯示 🔴 缺 5 人，不需要另外問同意

**例 14 · 地點不用同意**（D-16）
T+6天 有人回報「大全街側溝缺 10 人」
→ 直接顯示 🔴 缺 10 人，沒有同意這一層

**例 15 · 需求可以先於同意**（2026-09-27，01 未實作）
T+6天 09:00 鄰居回報「乙路 45 巷 6 弄 3 號缺 5 人」，屋主還沒被問過
→ 在「要先問屋主」分類，同一列標「尚未取得同意」和「缺 5 人」
→ 不出現在「可以直接幫忙」；要不要進門只看同意
T+6天 10:00 有人回報「已同意」
→ 移到「可以直接幫忙」，需求仍是 09:00 那筆「缺 5 人」

---


### 三個數字的定義

- **覆蓋率** = 曾經有過至少一筆回報的對象數 ÷ 對象總數
- **從未被確認的對象數**（以及它們從 T+0 到現在暗了多久）。原本寫成「平均暗了多久」，但那個值對所有從未被確認的對象都等於現在時間，沒有資訊量，因此改成個數。
- **白跑人次** = 到場後發現當地已經沒有剩餘工作的人次

⚠️ 時間一律用「災後第幾天幾點」（T+），不用真實日期。
