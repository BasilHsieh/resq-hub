# ResQ Hub — Vision

> **這份文件的狀態**：Positioning 一節已於 2026-09-01 對齊 [DECISIONS.md](../DECISIONS.md) 的 D-01／D-02。
> North Star 與 Vision 場景兩節**仍是 2026-04-18 的初稿**，等 Basil 重寫。標了 🚧 的段落請勿當成結論引用。

## Background

2025 年花蓮光復（馬太鞍溪堰塞湖溢流）的救災行動，讓我們看到：

- 民間志工動員能量極強——政府確認全期 **45 萬人次**——但資訊流極度分散
- LINE 群組與民間平台雖快速，但缺乏結構化資料與即時同步機制
- 許多需求被重複回報、志工重複出動，反而造成資源浪費
- 政府派工平台雖存在，但效率低落、難以與民間協作

想解決的不是「工具缺乏」，而是**缺乏可被複製的協作模式與資訊架構**。

## Positioning

> **2026-09-01 更新**：本節取代 2026-04-18 初稿的「聚焦團體間橫向溝通」。理由見下方「已否決的方向」。

**ResQ Hub ＝ emergence 層的協作基礎設施。**

不指揮、不媒合，只讓那個一直沒人管的民間自組織層**看得見、接得上**。

災區是雙層的：

| 層 | 誰 | 誰在管 |
|---|---|---|
| **上層** | 專業應變單位（搜救、醫療、警戒） | ICS／指揮控制體系 |
| **下層** | 散兵志工、臨時成型的群體、在地民間力量 | **沒有人** ← ResQ Hub |

核心命題：**組織性不是入場券，是一種可以被快速賦予的狀態。**
ResQ Hub 是一台讓任何人、任何臨時組合，在最短時間內取得「最低限度組織性」的機器——系統頒發的不只是調度，是**正當性**：讓素昧平生的人「有資格站在這裡」。

**三個立場**：
- **對志工透明優先，對政府透明其次**——政府是 bonus，不是 precondition
- **做共同視野，不做媒合**——市場從不「派」人，它廣播價格讓人自己流動
- **補 ICS 的結構盲區，不搶指揮權**——一個不搶權、只點亮盲區的東西，政府才可能放心納入

### 已否決的方向

| 方向 | 何時否決 | 為什麼 |
|---|---|---|
| **聚焦團體間橫向溝通** | 2026-06-27 | 誰會在不清楚價值的情況下分享資料？橫向溝通要求組織先讓渡資訊主權——它是**結果，不是入口** |
| **志工媒合** | 2026-06-26 | 媒合的前提是供需可掌控；災區兩邊都不可掌控，必然失敗 |
| **治理／指揮調度災區** | 2026-05 | 來自外部視角＋工程師思維，與現場的 emergent coordination 實況不符 |
| **把「政府邀請」當價值終點** | 2026-06-27 | NCDR 計畫白紙黑字排除公民回報；卡關的是信任與究責，不是資訊品質 |

## 介入窗口

工具**什麼時候進場、什麼時候退出**，是定位的另一半：

| | 時點 | |
|---|---|---|
| 系統上線 | T-∞ | SaaS 永遠在線，不是災後才架站 |
| 事件節點開啟 | T+0，冷啟動 ≤ 72h | 針對這場災害開一個節點 |
| **全效期** | **T+72h ~ T+3w** | 清淤期：低耦合、低失敗成本、99% 是協調問題 |
| 退場 | T+1m 起 | **不是關站，是移交**（封存／交重建期組織／交政府） |

**刻意不做兩端**：T+0~72h 急性搜救期（高耦合高失敗成本，屬 ICS）、T+1m 之後的長期重建期（月／年刻度，屬社工體系）。

詳見 [介入窗口_時間軸](../knowledge/framework/介入窗口_時間軸.md)。

## 🚧 North Star（待 Basil 重寫）

> 當前版本是**解法導向**，需改為結果導向：
> 「在任何災害現場，都只有一張共享的任務地圖與一種任務語言：人人看得懂、即時更新、可被複製。」

建議方向：改成可衡量的結果。但「用什麼衡量」本身還沒答案——資源錯配率？覆蓋率？冷區停留時間？見 [DECISIONS.md](../DECISIONS.md) U-09。

## 🚧 Vision 場景（待收斂）

> 讓台灣在面對災害或戰爭時，能快速動員、即時協作、降低混亂的「數位民防中樞」。

**此段範圍偏大**，且與已收斂的定位張力明顯：「民防中樞」聽起來像指揮，但定位明確說不指揮。v1 應聚焦單一災害場景，選颱風或地震見 [DECISIONS.md](../DECISIONS.md) U-07。

## 三層框架

**不只是系統，而是一個「框架」**——系統只是載體，重點是「知識如何被保存並重現」。

| 層次 | 目標 | 具體行動 |
|------|------|----------|
| 經驗層 | 整理光復救災的具體經驗與問題 | 收集案例、訪談志工、標註流程痛點 |
| 模式層 | 抽象出可被複製的志工協作模型 | 志工角色模板、任務資訊流架構 |
| 工具層 | 未來可發展的雲端系統與模組化工具 | 災情地圖、志工報到模組 |

這三層也是**開發順序**，不要跳過經驗層直接做工具。

## Problem Statement

1. **資訊來源分散**：通報、群組、民眾照片全散在各平台
2. **任務重疊／遺漏**：志工重複前往同一地點，真正需要的地方卻沒人去
3. **人力與物資調度低效**：現場和遠端資訊不一致，工具、物資去向難追蹤
4. **缺乏可回顧的資料紀錄**：事後很難分析哪些決策有效、哪些需改進
5. **網路訊息快但無法同步**

> ⚠️ 第 3 點（物資調度）落在**中高耦合子系統**，文獻一致指向需要組織化——不在 v1 的自組織模式射程內。見 [DECISIONS.md](../DECISIONS.md) U-06。

## 最大的未解問題

**需求資料從哪來？**

「讓志工看到需求」整個押在「需求資料能否即時、足量被收集」。災民自己報（最重災的人最沒能力報）／志工現場報（雞生蛋）／里長組織報（又多一層人力）——**不解決，透明層就是一張空地圖。產品成敗可能濃縮在此。**

見 [DECISIONS.md](../DECISIONS.md) U-01。
