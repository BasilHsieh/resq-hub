# 02 · 兵推多人版（規劃中，尚未實作）

> **狀態：只有規劃，沒有程式。** 決策見 [DECISIONS.md](../../../DECISIONS.md) 的 D-10（多人多裝置）與 D-11（Firebase）。
> 單機版在 [01-兵推](../01-兵推/README.md)，是這一版現場沒網路時的備援。規則的規格在 [資料模型與狀態機](../../spec/資料模型與狀態機.md)。

## 1. 要做什麼

一場兵推＝一個房間代碼。每個參與者用自己的裝置開自己角色的頁面、同時操作；主持人推進回合。

## 2. 頁面清單（按角色，不按地點）

| 頁面 | 給誰 | 裝置 | 做什麼 | 留／丟 |
|---|---|---|---|---|
| 入口 | 所有人 | 任何 | 輸入房間代碼、選角色（或掃主持人投影的 QR code） | 丟 |
| 志工頁 | 去幫忙的人 | 手機 | 我該去哪（含「今天不用來」）、離場回報 | 留 |
| 中繼站頁 | 中繼站的人（報到站、還鏟子點、物資站後面的人） | 筆電或平板 | 代為登記（連續輸入）、指路用的該去哪、本區彙整 | 留 |
| 遠端頁 | 遠端整理的人 | 桌機 | 聚合到村、過期與冷區清單、（之後）社群雜訊 | 留 |
| 主持台 | 兵推主持人 | 投影大螢幕 | 時鐘與回合、參數、注入事件、⚪ 圖層開關、結算。**模擬器只在這裡跑** | 丟 |

- 「災害現場」「指揮中心」不是頁面。**頁面跟著人走，不跟著地點**：現場有志工也有中繼站的人，他們用的是不同的頁面。
- **頁面按角色分，動作可以跨頁**：「回報」在志工手機上是一次一題，「代為登記」在中繼站筆電上是一列一列——同一份資料、不同形式。角色 × 動作的對照見 [角色輪廓](../../spec/角色輪廓.md) §0。
- **沒有「指揮」這個角色。** D-02 決定不指揮、不媒合。主持台是演習的導演，不是產品的一部分——所以它標「丟」。

## 3. 檔案怎麼分

一個靜態網站，五個 HTML 共用一支程式：

```
02-兵推多人/
  index.html                 入口
  vol.html  relay.html  rmt.html  host.html
  shared.js      留：資料模型、狀態規則、資料層接縫（從 01 搬過來，一字不改）
  firebase.js    丟：資料層接縫的 Firebase 實作
  scenario.js    丟：想定（家戶名單）
  sim.js         丟：模擬器，只有 host.html 載入
```

01 是單一個檔案，因為要雙擊就能開。02 走網址，所以可以拆檔——而且拆檔正好把「留／丟」變成實體的檔案界線，接手的人一看資料夾就知道哪些能丟。

## 4. 資料庫（Firebase Realtime Database，一棵 JSON 樹）

```
rooms/
  {房間代碼}/
    meta       想定版本、建立時間、⚪ 圖層開關、參數     ← 只有主持台能寫
    clock      現在時間、第幾回合                        ← 只有主持台能寫
    reports/   回報記錄，只增不改                        ← 人人可寫
      {自動編號}: { t, targetId, state, needPeople, source, note, revisitAt }
    events/    主持人注入的事件                          ← 只有主持台能寫
```

- **不放**家戶名單（在 `scenario.js`）、**不放**任何使用者資料、**不放**真實狀況（只在主持台的記憶體裡，參與者翻資料庫也看不到）。
- **狀態不存。** 每台裝置訂閱 `reports`，用 `shared.js` 同一套規則各自算出 🔴🟢⚪。與 spec §2「狀態由回報歷程推導」完全一致。

## 5. 誰能讀寫什麼（存取規則）

| 節點 | 讀 | 寫 |
|---|---|---|
| `meta` `clock` `events` | 有房間代碼的人 | 只有主持台（用主持人金鑰，在存取規則裡驗證） |
| `reports` | 有房間代碼的人 | 有房間代碼的人 |

### CRUD 在哪裡

沒有後端程式，不代表沒有 CRUD——是資料庫自己提供，規則負責限制：

| | 誰 | 對什麼 |
|---|---|---|
| Create | 人人 | `reports`；主持台另外可寫 `events` |
| Read | 人人 | 整個房間（訂閱，有新資料即推送） |
| Update | 只有主持台 | `clock`、`meta`——換值，不改歷史 |
| Delete | 沒有 | 回報永不刪除；一場結束後主持人在後台封存整個房間 |

回報沒有 Update／Delete 是 spec §2 的直接結果：狀態由回報歷程推導，新的一筆蓋過舊的、舊的留著（例 4）。「可信度靠更新頻率」的實作就是「不能改、只能加」。規則裡以「該節點尚不存在才允許寫入」強制，並驗證欄位與允許的狀態值。

- 沒辦工作坊時整個 `rooms` 關閉寫入（D-11 護欄 3）。
- 主持人金鑰怎麼做，實作時再定。沒有登入系統，這是「防誤觸」等級，不是資安等級——演習資料本來就不需要資安等級。

## 6. 邏輯在哪裡跑

- **狀態推導、褪色、結算**：每台裝置自己算（`shared.js`）。
- **模擬器**（志工怎麼流動、真實狀況怎麼變）：只在主持台的瀏覽器。主持人按「推進回合」→ 模擬器算出這回合發生的事 → 把產生的回報寫進 `reports`、新時間寫進 `clock` → 其他裝置收到更新，各自重算。
- **後端程式：零支。** Firebase 的存取規則與即時同步取代了後端。

## 7. 為什麼不用後端程式

後端能買到的能力，這一版一個都用不到，而它是整套裡最貴的資產（要部署、要日誌、會在看不到的地方壞掉）：

| 後端才有的能力 | 對兵推 | 對真產品 |
|---|---|---|
| 藏東西：金鑰、真實狀況放使用者碰不到的地方 | 真實狀況放主持人瀏覽器即可 | 要 |
| 複雜驗證：規則查得了欄位型別，查不了「與上一筆矛盾」「一秒寫十筆」 | 演習資料，無人攻擊 | 要 |
| 算一次、大家共用 | 幾十台裝置各算各的，零成本 | 幾萬台時要 |
| 接外部系統（政府 API、LINE），金鑰不能放前端 | 沒有外部系統 | 要 |
| 主持人的電腦不是單點 | 當機就重來 | 要 |

另兩個理由：D-11 已定兵推後端屬「丟」，替預定要丟的東西蓋最貴的部分不划算；邏輯留在 `shared.js`，真產品的工程師會用自己的技術把它搬進自己的後端，我們不該替他們預選。這種架構有正式名字（BaaS／serverless），不是權宜之計。

**接受的風險**：各裝置自算狀態，前提是同一版程式。舊頁面沒重整會算出不同顏色。解法：房間 `meta` 記版本號，版本不合的頁面拒絕進入並要求重整。

**加一支後端的觸發點**（用 Cloud Functions，仍非微服務）：要接外部資料、要做參與者不該自己做的運算、主持人的電腦當單點成為問題（例如遠距主持）。

## 8. 為什麼不是微服務

微服務是把一個系統拆成很多支各自部署、各自有資料庫、透過網路互相呼叫的小程式。它解決的是**大系統、多團隊、各功能要獨立上線**的問題；代價是每一支都要部署、監控、處理彼此對話失敗。

我們有**零支**後端程式，沒有東西可以拆。這不是簡化過頭，是規模剛好不需要：四個角色頁面、一個資料庫、幾十台裝置。

什麼時候會需要「一支」後端（仍然不是微服務）：要接外部資料（例如政府災情 API）、要做參與者不該自己做的運算、要寄通知。到時候用 Firebase 的 Cloud Functions 加一支小程式即可。真產品階段更可能是「一支後端＋一個 Postgres」（D-11 的邊界）。**可預見的任何階段都不需要微服務。**
