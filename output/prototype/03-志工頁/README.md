# 03 · 志工頁（互動版）

> **線上版**：https://claude.ai/artifact/VMPrFeT1KRDkLeGnv1U35N （用手機打開最準；最下面有「演習控制」和「所有狀態一次攤開」的連結）。預設只有 Basil 打得開，要給別人試，從頁面的 Share 選單分享。
>
> **演習用。所有地址、需求、時間都是編的**：地址用甲、乙、丙，刻意不像真實門牌，連結轉給別人時不會把「尚未取得同意」掛在真的房子上。
> 規格：[資料模型與狀態機](../../spec/資料模型與狀態機.md) §0d、§2、§7。設計：[角色輪廓](../../spec/角色輪廓.md) §1b、[設計系統](../../spec/設計系統.md)。決策：[DECISIONS.md](../../../DECISIONS.md) D-15、D-16、D-17、D-18、D-19。

## 1. 這一版是什麼

2026-09-28 起（D-18），志工頁不再先畫靜態 mockup，直接做成**可以點、要留下來的程式**：接手的人接著做，不重做。

- **清單**：最上面四個分類（可以直接幫忙／要先問屋主／不同意／暫時不用去），直接寫數量；下面一戶一張卡，只列走路 15 分鐘內，近的排前面。點一戶就地展開。
- **回報這一戶**：同意狀態和需求分成兩塊，各自更新，只填你知道的那一項（D-16）。公共區域只有需求那一塊。
- **一題一頁**：屋主同意嗎？這一戶還需要人嗎？還要幾個人？答案放在畫面下方。
- **回到清單**：上方多一張「你剛剛在」，做完要離開時回到那一戶更新需求。
- **演習控制**（不是產品的一部分）：讓時間往前 1 小時、3 小時、1 天，看「人夠了」三小時、「清完了」一天之後怎麼回到「可以直接幫忙」；「重來」會清掉這支手機上的紀錄。
- **所有狀態一次攤開**（`gallery.html`）：16 格，每一格都是同一份畫面程式配一組演習資料，取代原本的設計畫布。
- **每一格一張基準圖**（`screens/linux/`，D-19）：每個 PR 自動截圖比對，畫面變了卻沒有一起更新基準圖就過不了。規則有測試守著，長相有這一關守著。

## 2. 這一版的兩張清單（D-19：每張畫面都要附）

程式沒有空白——沒定的事，程式照樣會做點什麼。所以每做或改一張畫面，都把「替你決定的」和「還沒定的」攤開。

### Claude 替你決定的（D-13 補；Basil 可否決）

- 清單上的「最後更新」＝這一戶最近一筆回報的時間，同意或需求都算；回報頁的兩塊各寫各的時間。
- 每次回報都出現「已記下」。這一版只存在這支手機，所以不寫「下一個打開的人會看到」（設計系統 Notice 的規則）。
- 回報「人夠了」「清完了」之後，「你剛剛在」收起來：那代表你要離開了。
- 「怎麼走」這一版還沒有導航，按了只會提示。

### 還沒定的（程式現在的做法只是暫時的）

- 🚧 **進不去（⏸）的戶放哪一類、怎麼顯示**：暫時放「暫時不用去」、不顯示需求標籤，也沒有回報 ⏸ 的按鈕（[資料模型與狀態機](../../spec/資料模型與狀態機.md) §0d）。
- 🚧 **清單預設停在哪一類**：現在是「可以直接幫忙」；停在「要先問屋主」會不會讓更多人去敲門，交給兵推測（D-16）。
- 🚧 **要不要有地圖、導航**：對第一次到的外地志工，地圖有沒有用還不知道（[角色輪廓](../../spec/角色輪廓.md) §1 的問題 1）。
- 🚧 **網路不穩時「還沒送出」的樣子**：等做災時那一半（DECISIONS U-17）；在那之前，「下一個打開的人會看到」這種話不能寫。
- 🚧 **陽光下夠不夠清楚**：淺色塊和輔助文字還沒在戶外實測（[設計系統](../../spec/設計系統.md) 第 7 節）。

## 3. 刻意不展示什麼

別人的回報（這一版只有你一個人在按，資料存在這支手機）、人會不會散開或擠在同一戶（那是兵推的事，見 [01-兵推](../01-兵推/README.md)）、地圖、導航、出發前那一頁、中繼站與遠端頁、「問了很多次都沒結果」轉給問里長的人、登入、多人連線、網路不穩時的樣子、進不去（⏸）的戶。

## 4. 傳給別人試之前

請對方用手機照畫面上的情境點一輪，再問三題：

1. 你第一眼想點哪一戶？為什麼？
2. 按了「還沒問到」之後，你覺得下一個打開的人會看到什麼？
3. 哪裡看不懂、或按不到？

記對方的原話，不要先解釋。這是 D-15 核心假設（「看到沒人去過就會去」）與同意流程的第一批外部證據。


- **本機打開**：直接用瀏覽器打開 `app/index.html` 就行（React 從 CDN 載，要有網路）；畫面引用 repo 裡 `../../../design-system/components/` 的元件，所以要在完整的 repo 裡打開，不能單獨拿出這個資料夾。
- **發布**（Claude 用 Artifact 工具，更新同一個網址）：把 `app/` 的檔案和設計系統的 `bundle.css`、`bundle.js` 放進同一個資料夾（後兩者放在 `ds/`），`index.html` 與 `gallery.html` 裡的 `../../../design-system/components/` 換成 `ds/`；`index.html` 的外殼（doctype、html、head、body、charset、viewport）拿掉，平台會補上。
- **改畫面＝改程式**：人不在網頁上直接調整，都透過 AI 改 repo 再發布（D-17）。

### 畫面比對（D-19）

每個 PR，GitHub 會把 `gallery.html` 的每一格重新截圖，跟 `screens/linux/` 的基準圖比。不一樣、少一張、多一張都過不了；畫面連到 React 以外的外部網址也過不了。

- **基準圖只認 GitHub 跑出來的**（字固定為 Roboto 與思源黑體，也就是 Android 手機上的樣子）。Mac 的字型不同，在 Mac 上截的圖不能放進 `screens/linux/`；也因此基準圖不代表 iPhone 的樣子。
- **在 Mac 上先自己看一眼**（結果放在 `screens/darwin/`，不進 repo）：改畫面之前跑一次留底，改完再跑，就知道動到哪幾格。

  ```bash
  cd scripts/visual && npm ci && npx playwright install --only-shell chromium   # 第一次
  cd scripts/visual && npx playwright test                                       # 之後每次
  ```

- **畫面真的要變的時候**，順序不能換：
  1. 推上去讓 GitHub 跑（還沒開 PR 的分支：`gh workflow run kb-check.yml --ref <分支>`）。「畫面比對」會紅，並留下兩包檔案：`screens-diff`（變了的每一格各有 expected、actual、diff 三張圖）、`screens-linux`（照現在的畫面產生的整份新基準圖）。
  2. **先把前後對照給 Basil 看，他點頭才往下。** 不然這一關只是 Claude 自己放行。
  3. 把新基準圖放回 repo，commit、推上去，這次會綠：

     ```bash
     rm -rf "output/prototype/03-志工頁/screens/linux"
     gh run download <run id> -n screens-linux -D output/prototype
     ```

  4. PR 的 Files changed 會顯示每一張圖的前後對照；Basil merge 就是點頭。
- **新增、改名、拿掉一格**：改 `gallery.js` 那一格的檔名欄，再照上面的流程換基準圖。順序可以動，檔名不要跟著順序改。
- **新的一頁**（中繼站頁、遠端頁）有自己的「所有狀態一次攤開」時，在 `scripts/visual/screens.spec.js` 的 `GALLERIES` 加一行。
- **抓得到什麼**（2026-10-01 實測）：間距差 1px、字換一個、灰階差 6 都抓得到；顏色只差 2～4 抓不到，那種改動由 token 的檢查負責（顏色只能從 `tokens.json` 改）。它比的是「跟上一次點頭的樣子一不一樣」，不是「對不對」。
